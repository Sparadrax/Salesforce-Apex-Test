# Architecture

## Layout

```text
src/
  main/
    main.ts                  Application lifecycle only
    windows/main-window.ts   Native window creation and navigation policy
    database/                SQLite worker, migrations, store, client, and IPC
  preload/
    preload.ts               Typed, context-isolated desktop bridge
  renderer/
    index.ts                 UI bootstrap
    env.d.ts                 Window API declaration
    features/orgs/orgs.ts    Organization list and Add org dialog
    styles/global.css        Shared visual foundation
  shared/
    contracts/desktop-api.ts  Plain cross-process API types
```

The renderer imports shared contracts as types only. It cannot access Node, Electron, the filesystem, or secrets. Main and preload must never depend on renderer modules. Shared contracts must not depend on any process-specific module. The preload is bundled into one CommonJS file so it works in Electron's sandbox.

## Adding features

Put each UI feature under `renderer/features/<feature>/` and colocate its components, styles, and tests. Only extract shared UI after multiple features need it. Add native feature services under `main/features/<feature>/` when they are needed; keep IPC adapters separate from business logic. Define request, response, and desktop API contracts under `shared/contracts/`. Expose a named preload method per operation, with runtime input and sender validation in the main handler. TypeScript types alone do not validate IPC input.

Salesforce authentication and executing tests are future features. The org screen and offline deployment-result importer live in their own org feature modules. Do not add empty services, dependency injection frameworks, global state libraries, or generic repositories ahead of a concrete requirement.

## Performance

The UI uses static HTML and feature-scoped DOM updates, with no UI framework or polling. Org pages contain at most 50 rows. File parsing and imports run on the database worker. The window becomes visible when its first render is ready. Production bundles are generated by Vite; normal source checks do not rebuild them.

As features arrive, dynamically import heavy optional views; use async I/O for Salesforce and local data; bound concurrent requests; page large results; release listeners and cancel work on disposal. Offload substantial CPU work to workers. Cache only with explicit size limits and invalidation rules. Measure startup, bundle size, memory, and representative data workloads before claiming a performance improvement.

## Validation

Run `npm run check` for strict TypeScript, lint, formatting, and source tests. Per user preference, do not recompile/package after every change. Run `npm run package` and packaged integration checks when requested or needed to investigate a specific build issue. Source worker tests verify database/import logic without a production build. Windows checks do not establish macOS compatibility; test Mac builds on macOS before release.

## Local persistence

SQLite runs in a dedicated worker with transactional migrations, indexed cursor reads, bounded batches, and a bounded request queue. See [database.md](database.md) for API usage, storage location, limits, and maintenance. Keep future business rules in feature repositories and expose only named IPC operations. Do not run synchronous database work in main or renderer.

Migration 2 introduces the [SFCC relational model](sfcc-model.md) for orgs, runs, classes, and coverage. Schema SQL is versioned under `main/database/schema/`; process-independent row types live in `shared/contracts/sfcc-model.ts`.

Migration 3 adds retained deployment documents linked to their runs. Migration 4 adds run summaries and paginated test outcomes with a one-time archive backfill. See [org import](org-import.md) for supported Salesforce formats, staged import flow, and merge behavior. The database worker owns both generic records and the org repository on one SQLite connection. Main registers independent list and org windows and shares its sender authorization between the generic and org-specific IPC adapters. Window context and import-session ownership come from the main registry; URL parameters and renderer arguments cannot change an org window identity.

The org popup has a complete run picklist and a three-table [coverage explorer](coverage-explorer.md). Coverage queries live in a separate repository; automatic cursor loading lives in the renderer's shared scroll-table module. Migration 5 adds indexes for this drill-down without changing table data.

[Table behavior](table-behavior.md) documents scrolling, coverage colors, and transactional org deletion. Deletion is a list-window capability with a native confirmation; main closes that org's registered windows after the worker commits.

Shared table-sort headers provide accessible direction controls. Scroll-table sorting uses allowlisted worker queries and sort/scope-aware cursor boundaries from main/database/sorted-page.ts; local sorting is used only for the bounded plotted-history response. No runtime table or tooltip library was added.

Right-clicking an Apex class opens an independently registered [coverage-history window](coverage-history.md). Its org/class identity is set by main. History filtering and bounded aggregation run on the SQLite worker; SVG UI code and styles load lazily in history windows.

The org list also supports native JSON selection and an identity-aware review dialog, shared with org-window imports. Separate list-only IPC actions accept validated identity fields; org-window IPC derives its fixed identity from the registry. The existing worker transaction creates or reuses the org while saving the run, avoiding partial empty orgs on failure. Renderer feature modules share the importer without duplicating its loading, confirmation, cancellation and disposal behavior.
